# Fix: Multisig emergency-withdraw proposal expiry could be refreshed indefinitely

## Issue
`propose_emergency_withdraw` (`contracts/amm/src/lib.rs`, ~lines 898–959) reset
`MultisigProposalExpiresAt` to `env.ledger().timestamp() + MULTISIG_PROPOSAL_TTL_SECS`
on **every** call, even when the calling signer had already approved the same
recipient and **no new approval was added**. The `if !approvals.contains(&signer)`
guard only controlled whether a new entry was pushed — not whether the expiry was
refreshed.

`MULTISIG_PROPOSAL_TTL_SECS` (7 days) is meant to force a pending proposal to gather
quorum within a bounded window or lapse. Because the expiry was refreshed
unconditionally, a single already-approved signer could keep a stuck proposal
(e.g. 1 of 3 required approvals) alive **forever** by periodically re-calling
`propose_emergency_withdraw` with their own address and the same recipient —
defeating `ProposalExpired` as a freshness/security check on stale proposals.

## Root cause
The expiry write was not gated on whether the call actually advanced the proposal
(added a new approval).

## The fix
Gate the expiry refresh behind a new `added_approval` flag: the expiry is (re)set
**only when a new approval is recorded**.

```rust
let added_approval = !approvals.contains(&signer);
if added_approval {
    approvals.push_back(signer.clone());
}
// ... store recipient + approvals ...
if added_approval {
    env.storage().instance().set(
        &DataKey::MultisigProposalExpiresAt,
        &(env.ledger().timestamp() + MULTISIG_PROPOSAL_TTL_SECS),
    );
}
```

### Why this is correct
- A **brand-new proposal** (first proposal, or a recipient change which resets the
  approval set) starts from an empty approval set, so the proposer is a *new*
  approval and gets a fresh 7-day window — unchanged behaviour.
- An **already-approved signer re-calling** with the same recipient adds no new
  approval, so the expiry is left untouched and the proposal lapses on schedule.
- The expiry can no longer be refreshed indefinitely: approvals never contain
  duplicates and are only cleared on execution or a recipient change, so each
  signer can extend the window at most once (and only by genuinely co-signing).
- Legitimate co-signing still refreshes the window (real progress toward quorum),
  and quorum execution within the window still works — verified by tests.

The change is surgical: recipient/approvals writes, `MultisigProposalExecuted`
reset, and the `ms_proposed` event emission are all unchanged.

## Validation
- **New unit tests** (`contracts/amm/src/tests.rs`):
  - `test_multisig_reproposal_by_approved_signer_does_not_extend_expiry` — an
    already-approved signer re-proposing the same recipient does **not** extend the
    expiry; execution after the original TTL returns `ProposalExpired`.
    - Verified this test **fails on the original buggy code** (returns
      `InsufficientShares`, because the expiry was wrongly refreshed) and **passes
      with the fix** (`ProposalExpired`) — proving it catches the exact bug.
  - `test_multisig_new_cosigner_refreshes_window_and_quorum_executes` — regression
    guard: a genuinely new co-signer still refreshes the window and quorum execution
    still drains reserves to the recipient.
- **amm unit suite:** 74 passed (72 pre-existing + 2 new), 0 failed.
- **integration-tests (lib):** 9 passed (6 multisig + 3 upgrade), 0 failed.
- **integration-tests (v2_to_v3 target):** 7 passed, 0 failed.
- **WASM build** (`cargo build --release --target wasm32v1-none -p amm`): succeeds,
  116 KB (under the 200 KB CI limit). `cargo clippy -p amm` clean; `cargo fmt` clean.

     contract, causing a non-root-authorization panic on the minimum-liquidity
     self-mint during `add_liquidity`. Fixed to use the pool contract as LP admin

     `scenario_multisig_re_execution_returns_already_executed` configured quorum = 2
     but only ever collected 1 approval, so they could never pass. Added the missing
     co-signature so quorum is genuinely reached (matching the tests' stated intent).
